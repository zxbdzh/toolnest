# 安装与自动更新参考：Magpie 与 MyGo

调研日期：2026-11-12。用途：为 ToolNest 的 Windows 安装包与自动更新规格提供依据，不代表已经实现或通过升级测试。

用户已经确认：首版使用安装包交付，并支持自动更新，参考 Magpie 的机制；默认后台检查与下载，提示用户重启或在下次启动生效，不主动重启；使用 GitHub Releases 托管发布文件，并支持工具箱公共代理，软件更新及后续联网工具默认共用。检查频率、具体发布仓库、代理协议与认证支持、签名配置尚未确认。

## 参考对象与证据范围

Magpie 为 [yetone/magpie](https://github.com/yetone/magpie)，源码固定到提交 [`613e177b6b870110217a8ed7c35ea544ce6736f0`](https://github.com/yetone/magpie/tree/613e177b6b870110217a8ed7c35ea544ce6736f0)。本次仅阅读其安装、下载、界面更新、重启和发布代码；没有安装或升级参考软件，也没有完整审计其所有更新路径。

MyGo 能力依据 [安装与分发](https://mygo.run/docs/distribution)、[自动更新](https://mygo.run/docs/updates)、[Updater 插件](https://mygo.run/docs/plugins/updater) 的当前官方文档；实施前仍需锁定依赖版本，并以 Windows 构建验证行为。

## Magpie 已核实的做法

### 用户级安装与稳定程序位置

该版本 Windows 程序以单个可执行文件分发，源码明确说明没有独立安装器。从 Downloads、Desktop 或临时解压目录启动时，程序可以询问安装位置并复制自身，默认目标为 `%LOCALAPPDATA%\Programs\magpie\magpie.exe`，不需要管理员权限。

用户选择的自定义安装目录记录到 HKCU；后来再次打开下载文件时可以找到已安装副本。它保留原下载文件；从用户自选工具目录运行或便携模式时，行为不同，不会一概搬移程序。其命令行集成、PATH 修改等是 Magpie 自身的产品需求，不据此推导 ToolNest 也需要这些功能。

来源：[install.go](https://github.com/yetone/magpie/blob/613e177b6b870110217a8ed7c35ea544ce6736f0/internal/update/install.go)、[install_windows.go](https://github.com/yetone/magpie/blob/613e177b6b870110217a8ed7c35ea544ce6736f0/internal/update/install_windows.go)。

### 检查、下载与生效分开

界面更新器在启动约 5 秒后进入检查循环，默认按六小时间隔，设置允许修改或关闭自动检查。发现新版后通常立即下载到暂存位置；关闭自动下载时只报告新版，等用户点击下载。

更新器单独表达 checking、found、downloading、ready、error、blocked 等状态，并提供版本号、更新说明、下载进度、速度与阶段信息。已下载更新等待用户重启，也可以在退出时安装、下次启动生效；权限不足等情况会限制退出时的安装。

来源：[界面更新器](https://github.com/yetone/magpie/blob/613e177b6b870110217a8ed7c35ea544ce6736f0/internal/gui/update.go)。

### 暂存、下载重试与完整性校验

更新源 `https://usemagpie.ai/api/latest` 提供版本、说明和按平台区分的资源，资源包含大小与 SHA-256。下载中断可按有限次数重试并使用 HTTP Range 继续，长时间无数据会中止本次尝试。下载后校验完整文件；缺少校验值或校验不符则不接受。

暂存优先放在应用缓存，跨卷等无法直接替换的场景使用程序旁的隐藏暂存目录。网络下载还有备用地址和代理支持，但不能将这些全部视为首版工具箱的必要范围。

需要区分：本次所读 Windows 裸程序更新路径使用 SHA-256 校验，源码没有为它提供与 macOS 相同的签名校验流程。SHA-256 一致能校验内容与更新源给出的哈希一致，不等于独立的发布者签名验证。

来源：[下载、校验与暂存](https://github.com/yetone/magpie/blob/613e177b6b870110217a8ed7c35ea544ce6736f0/internal/update/update.go)。

### Windows 替换与失败回退

更新前进行可启动预检；Windows 运行中的可执行文件先改名保留，随后将新程序放到原位置。文件被占用时有等待与重试，换入失败时尝试放回旧程序。

重启时等待新进程报告已启动；无法启动、提前退出或在限定时间内没有报告时尝试恢复旧程序，并记住这个版本受阻，后台不会无限重复下载同一受阻版本，用户主动检查可以重试。

限制：这里的启动标记是进程启动握手，不证明完整 UI、数据迁移及业务均已健康；回退本身也可能失败并返回错误。不能宣传成任何更新故障都会无损自动恢复。

来源：[二进制替换与重启](https://github.com/yetone/magpie/blob/613e177b6b870110217a8ed7c35ea544ce6736f0/internal/update/update.go)、[启动握手与回退](https://github.com/yetone/magpie/blob/613e177b6b870110217a8ed7c35ea544ce6736f0/internal/update/blocked.go)。

### 根据业务忙闲安排重启

Magpie 的可选自动重启会等待正在进行的网关请求结束，也会考虑近期界面输入和打开的对话框。重启后可以保持主窗口显示或仅托盘运行的状态。用户发起重启、CLI 重启和自动重启存在不同策略，不应从其中一种路径推断所有更新都绝对不会中断业务。

ToolNest 可借鉴此思路，把 PATH 备份、恢复、导入和目录切换纳入忙碌状态；关键写入期间禁止版本替换和重启。此项是本项目的实施建议，具体状态协调与故障测试需要写入规格。

来源：[更新等待规则](https://github.com/yetone/magpie/blob/613e177b6b870110217a8ed7c35ea544ce6736f0/internal/gui/update_wait.go)、[重启入口及窗口恢复](https://github.com/yetone/magpie/blob/613e177b6b870110217a8ed7c35ea544ce6736f0/internal/gui/update.go)。

### 发布与更新源

源码仓库打版本标签后将发布任务交给 `yetone/magpie-releases`，由该发布仓库构建和发布产物，再镜像回源码仓库；应用更新源仍以发布仓库为准。发布流程校验产物数量，并处理重新发布旧版本时不应把它设为最新版本的情况。

这说明更新需要完整的发布链路，不能仅在界面放一个“检查更新”按钮。ToolNest 尚无已配置的远端和更新源，暂不创建或发布 release。

来源：[发布流程](https://github.com/yetone/magpie/blob/613e177b6b870110217a8ed7c35ea544ce6736f0/.github/workflows/release.yml)。

## MyGo 可复用的现成能力

| 能力 | 官方提供的支持 | 对 ToolNest 的含义 |
| --- | --- | --- |
| Windows 安装包 | NSIS 安装器，当前用户安装，开始菜单与卸载入口 | 满足用户选择 B，优先使用框架的构建产物 |
| 稳定安装目录 | 默认当前用户的 Programs，升级安装沿用已有位置 | 程序与 `%LOCALAPPDATA%\ToolNest` 数据分离 |
| 更新来源 | GitHub Releases 或自有 HTTPS 目录，可接 S3/R2 | 发布位置待确认，首版不必先自建更新 API |
| 更新校验 | 内嵌公钥核验更新归档及差分包的签名 | 发布私钥由构建／发布环境管理，不进入源码或客户端 |
| 增量更新 | 有适用差分时使用，失败回退到完整包 | 可复用；首版可靠性不应依赖差分包一定存在 |
| 原生更新窗口 | `plugins/updater/native` 提供说明、进度、稍后提醒、跳过版本等 | 可以复用原生组件与更新窗口，不必额外加入 WebView |
| 状态与偏好 | 检查／自动下载设置、最近检查、可用版本与变更回调 | 可在应用设置与托盘显示状态 |

官方默认插件的检查节奏为启动后约 10 秒、之后每天检查，可配置；这与 Magpie 的默认六小时不是同一个实现。不能把 Magpie 的默认值当作 MyGo 默认值。

MyGo `Update.Install` 在 Windows 会替换程序文件，当前进程可以继续运行，新版本在重新启动后生效。更新不会执行 NSIS 安装／卸载钩子，因此升级数据处理或自启维护不能只放在安装脚本中。自更新还要求安装位置可写，当前用户安装适合这一限制。

更新签名与 Windows Authenticode 代码签名是两件事：前者验证更新归档由持有发布私钥的一方生成，后者供 Windows 识别可执行文件／安装器的发布者。是否已有 Windows 代码签名凭据尚未核实，不把“使用签名更新”写成“Windows 安装器已经签名”。

## ToolNest 的建议方案与待定项

- **已确认**：Windows 11 x64 安装包、自动更新、按用户保存数据，快照可另选目录；更新默认后台检查和下载，生效重启由用户决定。
- **建议**：MyGo 生成用户级 NSIS 安装包，程序默认放入 `%LOCALAPPDATA%\Programs\ToolNest`；数据仍位于已确认的用户数据目录。
- **已确认 Q30**：卸载时移除程序与属于 ToolNest 的自启项，保留全部快照、设置和执行记录；此决定不授权清理当前机器的数据。
- **建议**：优先复用 MyGo 更新与原生 UI 能力；能否直接使用完整 updater 插件取决于它能否遵守任务忙碌时的替换与重启限制。必要时以 `mygo.Updater` 结合现成 UI 控件实现应用交互，不重写签名或下载校验算法。
- **已确认 Q27**：后台下载后由用户重启，或在下次启动时使用新版本，不主动重启。
- **已确认 Q28／Q33**：源码、规格、问题记录与 Releases 在同一公开仓库管理，发布安装包和签名更新文件；具体远端地址与许可证仍需明确。
- **已确认 Q29**：用户可设置工具箱统一代理，软件更新与后续联网工具默认共用；保存为应用配置，不修改 Windows 系统代理。具体协议与认证支持待实施前核实。
- **工程细化**：[正式规格](../specs/toolnest-v1.md)已给出稳定版、语义版本号、检查间隔及代理目标行为，并区分用户决定与工程默认值；实际依赖接入和端到端升级仍需验证。
- **发布前待配置**：具体发布仓库、项目许可证、更新发布密钥与公钥、Windows 代码签名状态。
- **需验证**：旧版本更新到新版本后设置、快照与计划保留；网络中断、错误签名、不可写目录或受阻启动时能保持可用状态；忙碌时不替换或重启。MyGo 文档没有给出与 Magpie 启动握手相同的完整回退保证，这一要求要单独实现或验证，不能直接宣称已有。
- **数据边界**：更新失败时回退程序与回退数据不是同一问题；未来若变更数据格式，应设计兼容或迁移方案。更新过程不应更改用户 PATH，也不应把更新检查与 PATH 自动备份计划混为一谈。
- **用户文案**：版本说明仅描述用户可感知的改动和必要操作；内部发布架构、校验细节和数据迁移技术记录放开发文档。

本轮仅完成资料核实与访谈文档更新，未安装工具链、生成密钥、构建安装包、创建远端或发布任何版本。
